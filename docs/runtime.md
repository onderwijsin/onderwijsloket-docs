# Runtime & Deployment

> **Configuration, environment management, and deployment targets**

This document defines runtime configuration, environment handling, and deployment for the
repository.

For focused Varlock and Proton Pass usage patterns, see [Varlock and Proton Pass](./environment.md).
For CI/CD workflows and deployment automation, see [CI/CD](./ci-cd.md).

## Configuration Overview

Project configuration is split across multiple layers:

### Plausible Analytics

- Plausible module configured in `nuxt.config.ts` for analytics tracking
- Self-hosted or cloud-based privacy-friendly analytics
- No personal data collection, cookie-free

### Robots Policy

- `robots.txt` is generated by `@nuxtjs/seo` from the `robots` block in `nuxt.config.ts`
- Global AI directives allow search indexing plus AI input/output use
- Global AI directives disallow AI training
- Non-production environments still follow the existing `site.indexable` policy

### Configuration Files

| File                        | Purpose                                     | Scope       |
| --------------------------- | ------------------------------------------- | ----------- |
| `nuxt.config.ts`            | Nuxt modules, runtime behavior, route rules | Application |
| `package.json`              | Runtime/dev scripts, quality/test scripts   | Project     |
| `docker-compose.valkey.yml` | Local Valkey service definition             | Development |
| `vitest.config.ts`          | Vitest projects and coverage thresholds     | Testing     |

### Config Directory (`config/`)

```
config/
├── constants.ts              # Static cross-runtime constants ONLY
├── head.ts                   # App head/meta defaults
├── identity.ts               # Site identity exports
├── helpers.ts                # Runtime mode/turnstile resolver helpers
├── routeRules.ts             # Typed route-rule builders + grouped cache policies
└── utils/
    └── modules.ts            # Shared build-time module setup helpers
```

**Principle:** `config/constants.ts` should be limited to actual static cross-runtime constants.
Feature-tuned UI config belongs with the owning feature.

## Environment Management

For complete Varlock and Proton Pass usage patterns, see
[Varlock and Proton Pass](./environment.md).

### Key Highlights

**Core Principles:**

- `envs/.env.schema` is the source of truth for environment keys
- Each environment (`development`, `preview`, `next`, `production`) has its own Proton Pass item
- **Build-time code** reads from `ENV` via Varlock (`import { ENV } from 'varlock/env'`)
- **Runtime code MUST** read from `useRuntimeConfig()` or module options, **NEVER** from `ENV`
  directly
- `API_TOKEN` remains private runtime-only for admin/cache style routes
- Public MCP discovery metadata is projected into `runtimeConfig.public.mcp` so client-side UI can
  build stable MCP and browser-deeplink URLs without hardcoding routes
- Non-sensitive defaults can live in `envs/.env.<environment>` files
- The `envs/env.d.ts` file is **auto-generated** by Varlock during install, `pnpm dev`, or
  typecheck. It is **excluded from git** and should not be manually edited or committed.

**Schema Organization:** The root schema imports sub-schemas from `envs/schemas/`:

- `core` - Shared app/runtime config
- `dev` - Local development flags
- `cloudflare` - Cloudflare worker and KV config
- `redis` - Node/Coolify Redis config
- `cloudinary` - Cloudinary media and API config
- `sentry` - Sentry configuration
- `directus` - Directus runtime and type generation

**Essential Commands:**

```bash
# Validate environment against schema
pnpm env:check

# Generate type definitions
pnpm env:typegen
```

**Runtime Boundary (Critical):**

> DO NOT read `ENV` from runtime app or server execution paths. Resolve env at build time through
> Varlock, project values into `runtimeConfig` or typed module options, then read them at runtime
> through `useRuntimeConfig()`.

This keeps runtime behavior portable across Coolify and Cloudflare targets.

**Build Requirements:**

- Vaults must be prefixed with `app-` (e.g., `app-onderwijsin-nuxt-v2`)
- See [CI/CD](./ci-cd.md) for non-interactive environment requirements and build debugging.

## Deployment Targets

This repository supports **two deployment targets** with different ownership models:

### 1. Coolify Deployment (Primary)

| Aspect              | Detail                                        |
| ------------------- | --------------------------------------------- |
| Runtime Target      | Nitro Node server                             |
| Nitro Preset        | `node-server`                                 |
| Build System        | Railpack on Coolify build server              |
| Deploy Ownership    | GitHub Actions orchestrating the Coolify API  |
| Trigger             | Manual `release.yml` workflow dispatch        |
| Build Memory        | 8 GB heap available to the build process      |
| Required Resource   | One Redis-compatible database per environment |
| Preview Deployments | Optional, can be enabled separately           |

**Operational Note:** There is a known Coolify build-server memory issue tracked in
[issue #39](https://github.com/onderwijsin/onderwijsin-nuxt-v2/issues/39).

**Release And Deploy Contract:**

- `release.yml` is the entrypoint for production release/deploy operations on `main`
- The workflow exposes `create_release` and `create_deploy` booleans
- At least one option must be selected
- When both are selected, deploy waits for release to finish successfully
- The Coolify deploy job resolves the target commit, updates the Coolify application to that commit
  SHA, triggers deployment, and waits for the deployment to finish
- The active build currently requires 8 GB of heap available on the build runner to avoid memory
  failures

**Recommended Environment Shape per Coolify Environment:**

- App environment variables for this repository
- Dedicated Redis/Valkey connection details for cache/storage
- Environment-specific third-party credentials where applicable

**Production Runtime:**

- Should start Nitro through `pnpm start`
- `pnpm start` preloads `./.output/server/sentry.server.config.mjs` via Node `--import`

### 2. Cloudflare Workers Deployment (Optional)

| Aspect                 | Detail                                   |
| ---------------------- | ---------------------------------------- |
| Runtime Target         | Cloudflare Workers module runtime        |
| Nitro Preset           | `NITRO_PRESET=cloudflare_module`         |
| Deploy Ownership       | GitHub Actions                           |
| Runner Platform        | Blacksmith runners                       |
| Preview Deployments    | Automated for eligible PRs               |
| Production Deployments | Manual via workflow dispatch             |
| Build Memory           | 8 GB heap available to the build process |
| Required Resource      | One KV namespace per environment         |

**Runtime Requirements:**

- `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in GitHub secrets
- `CLOUDFLARE_ENV`, `MODE`, and `NITRO_PRESET=cloudflare_module` environment variables

**Manual Local Build:**

```bash
# For Cloudflare Workers
NITRO_PRESET=cloudflare_module pnpm build
```

**Prerender URL shape:**

- Nitro prerendering is configured with `autoSubfolderIndex: false` so routes such as `/privacy`
  emit flat HTML files instead of `/privacy/index.html`
- This preserves the repository-wide canonical non-trailing-slash URL contract across static asset
  serving environments such as Cloudflare Workers

See [CI/CD](./ci-cd.md) for deployment workflow details, preview behavior, and worker deployment
contract.

## Cache/KV Backends

### Automatic Backend Selection

Backend selection is automatic based on `NITRO_PRESET`:

> **Important:** `NITRO_PRESET` must be explicitly set to either `node-server` or
> `cloudflare_module`.

| Environment       | Backend       | Connection         |
| ----------------- | ------------- | ------------------ |
| development       | filesystem    | Nitro default      |
| node-server       | Valkey/Redis  | From env vars      |
| cloudflare_module | Cloudflare KV | Binding + HTTP API |

### Node/Coolify Configuration

- Default production runtime uses a Valkey instance managed in Coolify
- In `nuxt.config.ts`, the `cache` module options provide Redis connection input from env vars
- During module setup, `modules/cache` validates that input and registers a custom Redis wrapper
  driver
- The driver stores sidecar metadata keys (`<key>$`) containing request path metadata

**Node Connection Environment Variables:**

- `REDIS_URL` (or `REDIS_HOST` + `REDIS_PORT`)
- `REDIS_USERNAME`
- `REDIS_PASSWORD`
- Optional: `REDIS_DB`, `REDIS_TLS`, `REDIS_TLS_REJECT_UNAUTHORIZED`

### Cloudflare Configuration

- In `cloudflare_module` builds, the cache module registers a custom Cloudflare KV binding wrapper
- Validates the Cloudflare KV API credentials needed for bulk delete
- The existing `getMeta()` path-based invalidation flow still works on Cloudflare
- Cache invalidation uses the KV HTTP bulk delete API and deletes both cache keys and metadata
  sidecars (`<key>$`)

**Cloudflare Runtime Environment Variables:**

- `CLOUDFLARE_WORKER_NAME`
- `CLOUDFLARE_CACHE_NAMESPACE_ID`
- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_KV_API_TOKEN`

### Validation

- `resolveCloudflareConfig()` validates Cloudflare KV runtime values before the Cloudflare runtime
  is accepted
- `CLOUDFLARE_KV_API_TOKEN` must include KV namespace read and write access

### Local Testing with Valkey

To test local Valkey-backed cache/KV:

```bash
# Start Valkey service
pnpm valkey:start

# Run Nuxt against Valkey
pnpm dev:redis

# Or run both together
pnpm dev:stack

# Stop the stack
pnpm dev:stack:stop
```

## Deployment Configuration Guardrail

**Keep implementation aligned with the default Coolify/Node deployment path.** Both Coolify
(Node.js) and Cloudflare Workers deployment targets must remain supported.

- Treat Cloudflare-specific configuration as **opt-in work** that should stay isolated behind the
  resolved Nitro preset
- Most runtime selection is automatic from `NITRO_PRESET` (which must be explicitly set to
  `node-server` or `cloudflare_module`), but each supported target still needs its own resource
  variables
- Deployment resources are **NOT** provisioned by the app repository

See [CI/CD](./ci-cd.md) for deployment target ownership details.

## Module Runtime Configuration

### Route Rules

- Production route rules are generated in `config/routeRules.ts` with an explicit
  `'/route': createRule(lifetime, options?)` pattern
- `createRule(...)` merges custom route-rule overrides with `defu(...)`, so nested `cache` and
  `headers` fields inherit defaults unless explicitly overridden
- `CACHE_LIFETIMES.SHORT`, `.MEDIUM`, and `.IMMUTABLE` are centralized cache lifetime constants
- `createRule(...)` writes the normalized Nuxt cache shape (`cache.maxAge` + `cache.swr`) and can
  optionally append a `cache-control` header

### Turnstile Module

The `turnstile` local module owns Turnstile runtime config projection:

- `turnstile.siteKey` / `turnstile.secretKey` are configured once in `nuxt.config.ts`
- Module setup mirrors them into `runtimeConfig.public.turnstile.siteKey` and
  `runtimeConfig.turnstile.secretKey`

### Resolve Runtime Module

The `resolve-runtime` module:

- Owns runtime preset normalization
- Injects `runtimeConfig.resolveRuntime.preset` for server/runtime branching
- For `cloudflare_module`, also injects Wrangler KV/observability config and the Cloudflare Sentry
  Nitro plugin
- When `SENTRY_UPLOAD_SOURCE_MAPS=true`, strips the upstream `sentry-rollup-plugin` from the final
  Nitro build by default
- Set `SENTRY_UPLOAD_NITRO_SOURCE_MAPS=true` to restore the upstream Nitro upload pass

### Nitro Preset Resolution

- `NITRO_PRESET` controls the Nitro runtime target (required)
- `node-server` -> Node.js server
- `cloudflare_module` -> Cloudflare Workers module runtime
