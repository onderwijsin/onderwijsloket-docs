# Varlock and Proton Pass

> **Environment management: Varlock for loading, Proton Pass for secrets**

This document provides a focused guide on Varlock and Proton Pass usage patterns in this repository.
For detailed runtime configuration, deployment, and environment handling, see
[Runtime & Deployment](./runtime.md).

---

## Core Model

This repository uses **Varlock** for environment resolution and **Proton Pass** as the shared remote
secret store.

### Key Principles

- `envs/.env.schema` is the **source of truth** for environment keys
- Each application environment has its own **Proton Pass item**
- **Build-time code** reads from `ENV` via Varlock
- **Runtime code** MUST read from `useRuntimeConfig()` or module options, NEVER from `ENV` directly
- Tracked non-sensitive defaults live in `envs/.env.<environment>`

---

## Repository Layout

### Varlock Configuration

- Varlock load root: `package.json` → `varlock.loadPath=./envs/`
- Source of truth: [`envs/.env.schema`](../envs/.env.schema)
- Generated typings: `envs/env.d.ts` (auto-generated by Varlock during install, `pnpm dev`, or
  typecheck; **excluded from git**)

### Auto-Generated `env.d.ts`

The `envs/env.d.ts` file is **auto-generated** by Varlock during:

- `pnpm install`
- `pnpm dev`
- `pnpm typecheck`

This file contains TypeScript definitions for environment variables and is **excluded from git** to
avoid polluting commit history with random strings. You should **never** manually edit or commit
this file. It is ephemeral and will be regenerated as needed in both local development and CI
environments.

### Environment Files

| File                    | Purpose                                                   |
| ----------------------- | --------------------------------------------------------- |
| `envs/.env.schema`      | Root environment contract                                 |
| `envs/.env.development` | Development defaults (tracked)                            |
| `envs/.env.preview`     | Preview defaults (tracked)                                |
| `envs/.env.production`  | Production defaults (tracked)                             |
| `envs/.env.next`        | Next environment defaults (tracked)                       |
| `envs/.env.local`       | Local overrides (gitignored)                              |
| `envs/env.d.ts`         | Auto-generated TypeScript definitions (excluded from git) |

### Build Flags

Tracked schema keys that control build behavior include:

- `DISABLE_PRERENDER` - disables Nitro prerendering globally
- `DISABLE_MARKDOWN_PRERENDER` - excludes markdown-specific prerender outputs such as `/raw.md` and
  `/raw/**/*.md`, `llms.txt`, and `llms-full.txt` while keeping runtime handlers available

### Schema Organization

The root schema stays intentionally small, keeping only:

- `APP_ENV`
- `PROTON_VAULT`
- `PROTON_PASS_PERSONAL_ACCESS_TOKEN`
- `MODE`

The root schema imports **sub-schemas** from `envs/schemas/` using Varlock `@import(...)`
decorators:

| Sub-schema       | Purpose                                                                    |
| ---------------- | -------------------------------------------------------------------------- |
| `core.env`       | Shared app/runtime config, including Turnstile and webmanifest icon fields |
| `dev.env`        | Local development flags and values NOT stored in Proton Pass               |
| `cloudflare.env` | Cloudflare worker and KV config, excluding `TURNSTILE_*`                   |
| `redis.env`      | Node/Coolify Redis config                                                  |
| `cloudinary.env` | Cloudinary media and admin API config                                      |
| `sentry.env`     | Sentry runtime and source map upload config                                |
| `directus.env`   | Directus runtime and type generation config                                |

**Note:** These sections mirror the Proton Pass item sections used by the team.

## Proton Pass Configuration

### Vault Naming

- Proton Pass vaults for application env data **MUST** be prefixed with `app-`
- This repository uses the vault configured through `PROTON_VAULT`, e.g., `app-onderwijsin-nuxt-v2`

### Environment Item Structure

Each environment must have its own Proton Pass item inside the app vault:

- `development`
- `preview`
- `next`
- `production`

**Requirements:**

- Each item stores **one field per environment key**
- Field names must **exactly match** Varlock env key names
- Sensitive values go in Proton Pass, non-sensitive defaults go in tracked `envs/.env.<environment>`
  files

**Examples of Proton Pass fields:**

- `NUXT_PUBLIC_SITE_URL`
- `CLOUDFLARE_WORKER_NAME`
- `CLOUDFLARE_CACHE_NAMESPACE_ID`
- `API_TOKEN`
- `FAVICON`, `APP_ICON`, `MASKABLE_APP_ICON`

### Non-Environment Items

Other Proton Pass items and fields are allowed in the vault:

- CI helper items
- Backup records
- PAT storage items
- Operational notes stored as secure items

**Important:** These items are NOT used by application code unless explicitly referenced by the
schema.

## Team Access and Collaboration

### Vault Sharing

- The app vault **must** be shared with team members working on the codebase
- Team members need access for both local development and validating build-time env changes

### CI and Build Environments

CI and other non-interactive build environments must provide a Proton Pass personal access token.

**Repository-specific detail:**

- The environment variable name is `PROTON_PASS_PERSONAL_ACCESS_TOKEN`
- GitHub Actions also provides `PROTON_VAULT` so CI can resolve shared operational fields from the
  correct app vault
- Set this variable in:
  - GitHub Actions secrets
  - Coolify build environment
  - Any other non-interactive build runner

**Integration:** The shared GitHub Actions setup installs `pass-cli`, then Varlock uses the
PAT-backed Proton Pass CLI session during build steps.

### Shared CI Item

CI workflows may also read non-environment operational values from the `ci` item in the vault
selected by `PROTON_VAULT`.

Current fields used by GitHub Actions include:

- `CLOUDFLARE_PREVIEW_DEPLOYMENTS`
- `COOLIFY_URL`
- `COOLIFY_APP_UUID`
- `COOLIFY_TOKEN`

## Local Development

### Varlock + Nuxt/Vite Integration

- `pnpm dev` runs directly through `pnpm dev` — Nuxt works with Varlock Vite auto-load enabled
- Build-time code should use `import { ENV } from 'varlock/env'`
- The Vite integration injects required auto-load behavior for SSR and build
- Non-integrated scripts run through `pnpm exec varlock run -- ...`

### Local Encryption

For local-only secrets, **prefer Varlock local encryption** instead of storing plaintext values in
`envs/.env.local`.

**Benefits:**

- Keeps local overrides in gitignored env files
- Avoids raw secret values on disk in plaintext
- Maintains security while allowing local customization

**Use cases:**

- Local API keys that should not live in Proton Pass
- Machine-specific overrides
- Temporary secrets for local development

**See:** [Varlock Local Encryption Guide](https://varlock.dev/guides/local-encryption/)

## Practical Workflow

### Adding or Changing Environment Keys

1. Update `envs/.env.schema`
2. Add or update the matching field in each relevant Proton Pass environment item
3. Add tracked defaults to `envs/.env.<environment>` **only** when the value is intentionally
   non-sensitive and should live in git
4. Run `pnpm env:check`
5. Run `pnpm env:typegen` when needed

### Runtime Boundary (CRITICAL)

**DO NOT** read `ENV` from runtime app or server execution paths.

**Use this pattern instead:**

1. Resolve env at build/module setup time through Varlock
2. Project the values into `runtimeConfig` or typed module options
3. Read them at runtime through `useRuntimeConfig()`

**Why:** This keeps runtime behavior portable across Coolify and Cloudflare targets.

## Troubleshooting

### Operational Gotcha: Duplicate Proton Pass Items

If Proton Pass contains multiple items with the same environment name, resolution can become
misleading.

**Failure pattern:**

- Active item exists with correct fields
- Trashed duplicate with the same item name also exists
- Varlock/Proton resolution reports `Field does not exist: <KEY>` even when the active item contains
  the correct field

**Solution:**

1. Check for duplicate items with the same environment name
2. Check whether older duplicates are in `Trashed` (not just `Active`)
3. Remove or permanently clean up trashed duplicates that shadow current environment items

**This is especially important for:** `preview`, `next`, `production`
